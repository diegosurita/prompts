# Spec Plan

Use this skill to produce a machine-readable plan that orders the specifications in `.specs/` and maps the dependencies between them. The plan is written as a YAML manifest (`.specs/plan.yaml`) that an engineer or a Generative AI can follow to implement the specs in a correct, dependency-respecting order.

Ordering of tasks *within* a single spec stays in that spec's *Implementation Tasks* table — this skill only orders specs relative to each other.

Modes:

- **Generate / Update**: scan `.specs/`, (re)build the dependency graph, and write `.specs/plan.yaml`.
- **Validate**: check an existing `.specs/plan.yaml` for cycles, missing files, unknown dependency ids, and drift from the specs on disk.
- **Next**: report the spec(s) that are ready to implement now, based on status and order.

## When to Use

- Two or more specifications exist (or are planned) and you need the order in which to implement them.
- A spec was added, removed, renamed, or had its dependencies changed, and the plan must be refreshed.
- You need to know which specs are unblocked and safe to start.

## Where Dependencies Come From

Resolve each spec's direct dependencies using the following precedence. Prefer the first source that yields an explicit answer; use inference only to fill gaps.

1. **Explicit declaration (canonical).** A `depends_on` list in the spec's YAML front matter, naming other spec ids:
   ```yaml
   ---
   title: Authentication Login Endpoint
   depends_on: [schema-user-account]
   ---
   ```
   This is the preferred, deterministic source.
2. **Inference (fallback for specs without `depends_on`).** Derive candidate edges from spec content:
   - **Interface producer/consumer**: if this spec's *Interfaces & Data Contracts* (section 4) consumes a schema, endpoint, or data contract that another spec defines, it depends on that spec.
   - **Cross-spec links**: links in *Related Specifications* (section 11) that point to another `.specs/*.md` file, when the prose frames them as prerequisites ("requires", "builds on", "after", "depends on").
   - **Category heuristic**: a `data`, `tool`, or `process` spec that operates on entities defined by a `schema` spec depends on that schema spec.

   Treat inferred edges as candidates. When the relationship is ambiguous, list the inferred edges and confirm with the user before relying on them.

Do **not** turn *Dependencies & External Integrations* (section 8) into graph edges — those are external systems and services, not specifications. You may optionally record them per spec under `external` for reference; they never affect ordering.

When you infer or confirm an edge, offer to persist it into the dependent spec's front matter as `depends_on`, so future runs are deterministic.

## Procedure

1. **Discover.** List every `*.md` file in `.specs/` (ignore `plan.yaml` and any non-spec files). Each file is a spec; its `id` is the filename without `.md` and must match `[a-z0-9-]+`.
2. **Parse.** For each spec, read its front matter (`title`, optional `depends_on`) and its sections. Determine:
   - `category`: the high-level purpose prefix of the id — one of `schema`, `tool`, `data`, `infrastructure`, `process`, `architecture`, `design`.
   - `status`: aggregate of the *Implementation Tasks* table (section 12) — `blocked` if any task is blocked, else `in-progress` if any task is in-progress, else `completed` if tasks exist and all are completed, else `pending`.
3. **Build edges.** Resolve `depends_on` for every spec per *Where Dependencies Come From*. Every id in a `depends_on` list must be an existing spec id; flag unknown ids.
4. **Detect cycles.** If the dependency graph contains a cycle, do not invent an order. Record each cycle under `cycles` and surface it to the user for resolution before continuing.
5. **Order into waves.** Topologically layer the acyclic graph:
   - Wave 1 = every spec with an empty `depends_on`.
   - Wave N = every remaining spec whose dependencies are all satisfied by waves `1..N-1`.
   - Within a wave, sort ids alphabetically (specs in the same wave are independent and may be implemented in parallel).
6. **Write** `.specs/plan.yaml` using the schema below. Sort the `specs` list by `id`, keep field order stable, and keep sorting deterministic so re-runs produce minimal diffs.

## Output: `.specs/plan.yaml`

Location: always `.specs/plan.yaml`. Format: well-formed YAML. Schema:

```yaml
# Implementation plan for the specifications in .specs/.
# Generated by the spec-plan skill. Re-generate after adding, removing, or re-scoping a spec.
version: 1                      # plan schema version
generated: 2026-06-11           # date the plan was generated (YYYY-MM-DD)

specs:                          # one entry per specification, sorted by id
  - id: data-user-import        # = filename without .md; matches [a-z0-9-]+
    title: User Bulk Import Pipeline
    path: .specs/data-user-import.md
    category: data              # schema | tool | data | infrastructure | process | architecture | design
    status: pending            # pending | in-progress | completed | blocked
    depends_on: [schema-user-account]
  - id: schema-user-account
    title: User Account Schema
    path: .specs/schema-user-account.md
    category: schema
    status: pending
    depends_on: []             # ids of specs that must be implemented first
  - id: tool-auth-login
    title: Authentication Login Endpoint
    path: .specs/tool-auth-login.md
    category: tool
    status: pending
    depends_on: [schema-user-account]

order:                          # topological waves; specs in a wave have no interdependencies
  - wave: 1
    specs: [schema-user-account]
  - wave: 2
    specs: [data-user-import, tool-auth-login]

cycles: []                      # each item is an ordered id list forming a cycle; must be empty for a valid plan
```

### Field reference

| Field | Required | Description |
|-------|----------|-------------|
| `version` | yes | Schema version of this manifest. |
| `generated` | yes | Date generated, `YYYY-MM-DD`. |
| `specs[].id` | yes | Spec id (filename without `.md`). |
| `specs[].title` | yes | Title from the spec front matter. |
| `specs[].path` | yes | Path to the spec file from the repo root. |
| `specs[].category` | yes | High-level purpose prefix of the id. |
| `specs[].status` | yes | Aggregate status derived from the spec's *Implementation Tasks*. |
| `specs[].depends_on` | yes | Ids of specs that must be implemented first (`[]` if none). |
| `specs[].external` | no | Optional list of external dependency ids (EXT/SVC/INF/DAT/PLT/COM) for reference; not used for ordering. |
| `order[].wave` | yes | 1-based wave number. |
| `order[].specs` | yes | Spec ids in the wave, alphabetically sorted; safe to implement in parallel. |
| `cycles` | yes | Detected dependency cycles; empty for a valid plan. |

## Validate Mode

Given an existing `.specs/plan.yaml`, report (do not silently fix) every problem found:

- A spec file on disk has no entry, or an entry references a missing file (drift).
- A `depends_on` id does not match any spec id.
- The graph contains a cycle.
- The `order` waves are inconsistent with `depends_on` (a spec appears before one of its dependencies).
- `generated` predates the most recent change to a spec file (stale).

After reporting, offer to regenerate the plan.

## Next Mode

Using `status` and `order`, list the spec(s) ready to start now: status is `pending` or `in-progress` and every id in `depends_on` has status `completed`. Present them in wave order, and name the dependencies that still block the remaining specs.
